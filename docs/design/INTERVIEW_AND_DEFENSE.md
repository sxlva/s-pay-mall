## 1. 问题背景

### 1.1 这份教材解决什么

前几份教材解决"懂"，这一份解决"说"：

- **秋招简历**：3~4 条 bullet，每条都要有源码或测试证据兜底；

**夸大是负收益**。你在东软实习过，面试官大概率用"聊实习项目的方式"聊这个毕设：追问细节、追问数字、追问"你当时为什么不用 X"。每一条经不起追问的表述，都会把整场面试的信用拉低。本项目真实的设计密度（幂等、状态机、三道防线、条件更新裁判）已经足够支撑一份有竞争力的简历——**需要删除的是水分，不是亮点**。

## 2. 前置知识（约 20 分钟）

### 2.1 七问论证法

每个升级点统一按七个维度论证（你在大纲中亲自定下的结构）：

| 维度 | 要回答的问题 |
|------|-------------|
| 现状 | 当前代码如何实现？（源码锚点） |
| 问题 | 什么条件下暴露缺陷/瓶颈？ |
| 改造 | 具体改哪些模块和数据结构？ |
| 收益 | 一致性/吞吐/可维护性/可观测性，哪一项？ |
| 成本 | 新复杂度、运维成本、新故障点？ |
| 验证 | 什么测试证明改造有效？ |
| 面试表达 | 一分钟讲清"为什么值得做" |

**本节之后的核心训练**：给你任意一个升级点，90 秒内过完七问。

## 3. U-1 ~ U-5 七问论证（本教材核心）

> 每个升级点先给七问表，再给"面试一分钟版"。源码锚点均已核实。

### 3.1 U-2 发送端 Outbox（★ 最高频追问，重点掌握）

| 维度 | 论证 |
|------|------|
| 现状 | 支付回调事务提交后，`RocketMqOrderEventPublisher.publishPaySuccess` 直接 `syncSend`（`RocketMqOrderEventPublisher.java` L34-35）；发送失败 catch-all 仅记日志（L37-40）。事务与发送之间存在 W1 崩溃窗口（教材三 §5.2） |
| 问题 | 进程在"事务提交后、发送前"崩溃 → `order_paid` 永久丢失。重试、DLQ 都救不回，因为消息从未到达 broker。当前职责下只损失微信通知（前提 P1-P3）；**若消费端未来承担库存/履约，此缺口立即升级为资损级** |
| 改造 | 回调事务内同事务插入 `message_outbox` 表（`id`、`biz_no` 唯一索引、`topic`、`payload`、`status`、`retry_count`、`next_retry_time`）；新增 Job 扫描待发送记录同步发送，失败退避重试、超限告警；消费端幂等保持不变 |
| 收益 | 一致性：关闭"发出时丢"缺口，DB 提交与待发送记录原子一致 |
| 成本 | 一张表 + 一个 Job；重扫重发是预期行为（at-least-once 语义不变），排查链路多一跳 |
| 验证 | 注入"事务提交后、发送前崩溃"（如发送端抛异常/断点杀进程），验证 outbox 记录存在且 Job 最终发出、消费端去重正确 |
| 面试表达 | "事务和发消息是两道门，中间有崩溃窗口。现在的方案是接受这个窗口（职责限于通知），根治方案是 outbox：把'要发消息'和事务写在一起，让数据库替我们记住没发完的事。" |

**一分钟版**："支付状态推进在回调事务内同步完成，消息在事务提交后发送，中间有毫秒级崩溃窗口可能丢消息。当前 MQ 只承担微信通知编排，丢了人工可补，所以我接受了这个窗口；如果消费端要承载履约这类资金语义，就必须上 outbox——事务里插一张本地消息表，后台 Job 补发，用数据库的原子性关掉这个窗口。这是设计不是遗漏，并且我知道它的适用边界。"

### 3.2 U-3 消费记录表替代 Redis 单键

| 维度 | 论证 |
|------|------|
| 现状 | 消费幂等用单个 Redis 键 `stock:event:order_paid_notify:{orderNo}`，值恒 `PROCESSING`，24h TTL；异常时 release、成功等过期（`IdempotentGatewayImpl.java` L50-64；`OrderPaidRocketListener.java` L48-65） |
| 问题 | 两个竞态：①SETNX 与业务提交非原子——宕机中间态导致重放被误跳（W3 窗口，教材三 §5.2）；②"处理中/已完成"共用一个键，24h 后语义消失 |
| 改造 | 新增消费记录表 `(consumer_group, biz_no)` 唯一索引，插入记录与业务变更放**同一 DB 事务**：提交成功唯一索引拒重，宕机回滚则记录消失、重投自然重执 |
| 收益 | 一致性：把幂等从"24h 窗口的尽力抑制"升级为"与业务原子的一致性" |
| 成本 | 多一张表、每次消费多一次写；DB 成为消费热点（需评估）；外部副作用（微信通知）仍进不了事务，只能接受至少一次 |
| 验证 | 杀进程注入 W3 窗口，验证重启后重投正确处理（不漏不重） |
| 面试表达 | "Redis SETNX 是窗口内抑制，不是一致性。把幂等记录和业务写进同一个事务，是唯一让'幂等'和'生效'原子化的办法。" |

### 3.3 U-1 对账补偿 Job（部分落地，表述最讲究）

| 维度 | 论证 |
|------|------|
| 现状 | ⚠️ 已落地：Job 分布式锁 + 40 分钟兜底关单（`NoPayNotifyOrderJob.java` L40-43、L103-115）；❌ 未落地："pay_order=PAID 但主单未推进"的补偿分支 |
| 问题 | 后者场景：回调事务异常中断导致 pay_order 已 PAID 而 order_main 未推进——当前由晚到支付异常路径（ERROR 日志 + 人工）覆盖 |
| 改造 | Job 增加扫描分支：`pay_order=PAID` 且主单非 PAID、超过 5-10 分钟 → 调 `paySuccess` 补偿（状态机天然幂等） |
| 收益 | 可观测性/一致性：把"人工看日志"变成"系统自动补" |
| 成本 | 一个 SQL 分支；需确认与 MQ 消费并发的安全性（状态机条件更新已保证） |
| 验证 | 手工构造 pay_order=PAID + order_main=CREATED 的脏数据，跑 Job 验证被补偿 |
| 面试表达 | "我们的兜底思路是两条腿：消息链路内的重试+DLQ，和消息链路外的对账 Job。前者已实现大部分，后者关单方向已落地、支付方向登记为二期——因为当前回调事务内同步推进，脏数据概率极低。" |

### 3.4 U-4 Listener 异常分类

| 维度 | 论证 |
|------|------|
| 现状 | 所有消费异常一律重抛走 broker 重试（`maxReconsumeTimes=5`）；反序列化失败、订单不存在这类**不可恢复**错误也重试 5 次才进 DLQ |
| 问题 | 不可恢复错误重试是纯浪费：占用重试配额、延迟真正可恢复错误的恢复时间 |
| 改造 | 异常分类：可恢复（DB/Redis 抖动）重抛重试；不可恢复（数据格式错、订单不存在）记 ERROR 后直接 ACK |
| 收益 | 可维护性/可观测性：重试资源只花在可能成功的消息上 |
| 成本 | 一次异常分类的代码重构 + 开发规范补充；误判"不可恢复"会丢消息（需评审把关） |
| 验证 | 注入 poison message（坏 JSON），验证只告警一次、不进重试 |
| 面试表达 | "重试是有成本的资源，不该花在永远失败的消息上。当前是粗放式全重试，改进方向是按异常分类——这是运维成熟度问题，不是正确性问题，所以排在 U-2/U-3 之后。" |

### 3.5 U-5 DLQ 监控告警与重放（部分落地）

| 维度 | 论证 |
|------|------|
| 现状 | ⚠️ 已落地：`DlqAlertListeners` 两个 DLQ 告警监听器，ERROR 日志 + 消息体落痕（`DlqAlertListeners.java` L28-48）；重放靠 RocketMQ 控制台手工"重新发送"（L13 注释）；❌ 未落地：消息量>0 即告警的监控规则、自动化重放工具、外部通知渠道 |
| 问题 | 只告警不处理 = 静默丢消息的体面形式；手工重放依赖人记得 |
| 改造 | 监控侧：对 `%DLQ%` 主题消息量配置告警阈值；工具侧：自动化重放脚本（重放前校验幂等键 TTL）；流程侧：操作手册 + 工单流转 |
| 收益 | 可观测性：死信从"日志里有"变成"有人管" |
| 成本 | 监控配置与脚本维护；自动化重放必须处理幂等键残留（重放被 SETNX 误跳）这一前置问题（依赖 U-3） |
| 验证 | E3 实验（教材三 §6）产生死信后验证告警链路端到端 |
| 面试表达 | "死信处理的完整闭环是告警→定位→重放→复核。我们落地了第一步（日志告警+留痕），后面三步是生产化二期。我知道为什么不做：自动化重放依赖幂等键语义先升级，顺序不能反。" |

### 3.6 选讲：教材四遗留的两个候选升级点

**库存对账补偿（教材四 §5 场景 5）**：DB 扣减失败只记 WARN（`OrderStateMachineServiceImpl.java` L91-95），漂移会累积。改造：失败写对账表 + 定时对账 Job 按 Redis 预扣流水校准账面；成本一张表；收益可观测性。一分钟版与 U-2 同构："先让系统看见，再让系统自愈。"

**通知必达化（教材三 §5.3）**：微信通知异常被吞、无补偿。改造：通知记录表 + 重试任务；或明确接受 best-effort 定位。答辩被问"用户没收到通知怎么办"时，这是标准答案的两条分支。

## 5. 简历成稿

### 5.1 四条 bullet（每条带证据锚点，可独立经受追问）

> **s-pay-mall 电商商城系统**（个人毕业设计项目，DDD 分层架构，Spring Boot 2.7 / Java 17 / MySQL 8 / Redis / RocketMQ）

1. **防超卖三层库存体系**：设计"Redis 原子预扣（负数自动补偿）+ MySQL 条件更新落账（`WHERE stock >= n`，影响行数即并发裁判）+ 取消/关单事务提交后恢复 Redis（规避 Redis 无法随 DB 回滚的超卖窗口）"的两层库存架构；下单幂等基于 requestId 的 SETNX 键（24h）+ 用户级短锁降级。
   *证据*：`StockGatewayImpl.java` L42-49、`IProductDao.java` L31、`OrderApplicationService.java` L169-217、L497-503；并发防超卖压测 2026-10-19 实测通过（`docs/dev-ops/stock-pressure-test.sh`，20 并发抢 5 件：成功 5、无 Redis 负值、DB 订单数一致）。
2. **支付可靠性闭环**：支付宝异步通知在事务内完成订单/支付单状态推进与库存落账（条件更新防并发重复推进），事务提交后发送 `order_paid` 事件；消费端 Redis SETNX 幂等（24h 窗口抑制重投）+ `maxReconsumeTimes=5` + DLQ 告警监听器（ERROR 留痕、控制台人工重放）；关单前三道防线（30min 延时消息二次确认支付宝交易状态 / 40min 定时兜底 / 用户取消）汇聚于状态机条件更新，天然幂等。
   *证据*：`OrderApplicationService.java` L369-392、L470-488；`OrderPaidRocketListener.java` L43-67；`NoPayNotifyOrderJob.java` L57-115；`TimeoutCloseOrderE2EIT`（三场景，2026-10-19 复跑通过）。
3. **消息中间件技术演进**：项目事件机制经历 Guava EventBus（进程内）→ RabbitMQ → RocketMQ 三阶段演进（Git 历史可查），迁移驱动力为可靠性需求升级（进程内事件重启即丢 → 需 broker 持久化/重试/死信）；RocketMQ 落地延时消息（关单）、消费重试与 DLQ 告警。
   *证据*：提交 `07ea1b7`/`03314db`/`10b3129`；`OrderPaymentGatewayImpl.java` L35-47；`DlqAlertListeners.java`。
4. **DDD 分层与幂等设计体系**：按 Trigger→Application→Domain←Infrastructure 分层约束依赖方向，库存预检查等业务语义下沉 Domain 层、Gateway 仅保留原子操作；统一幂等网关（SETNX/释放/完成标记）复用于下单、支付回调、MQ 消费三链路；补偿 Job 以 Redisson 分布式锁（`tryLock(0,60s)`）防多实例重入。
   *证据*：`MallOrderServiceImpl.java` L44-65（L39-40 DDD 注释）；`IdempotentGatewayImpl.java` 全文；`NoPayNotifyOrderJob.java` L59-64。

### 5.2 简历注意事项

- **不写没跑过的数字**：吞吐、并发、耗时一律不写（除非你先做完压测）。
- **实习与毕设分开**：东软实习经历单独成条；毕设项目不要借用实习的流量描述。

## 6. 答辩讲稿

### 6.1 五分钟版（标准陈述）

> 各位老师好，我的题目是《基于 DDD 的电商商城系统的设计与实现》。系统采用 Spring Boot + MySQL + Redis + RocketMQ，按领域驱动设计分为触发、应用、领域、基础设施四层，实现了微信扫码登录、购物车下单、支付宝支付、超时关单与管理后台。
>
> 架构上我想强调两点。第一，**支付一致性**：支付宝异步通知到达后，我在一个数据库事务内完成订单状态、支付单状态和库存落账三步，用条件更新做并发裁判——同一笔支付并发到达时，数据库影响行数保证只有一方生效；事务提交后才发送 RocketMQ 事件用于异步通知。第二，**库存防超卖**：下单在 Redis 原子扣减，扣成负数自动补偿拒绝；支付成功才把预扣落到 MySQL 账面；取消和超时关单在事务提交后恢复 Redis——因为 Redis 不参与数据库事务，提前恢复会在回滚时造成超卖。
>
> 超时关单我设计了三道防线：下单时发 30 分钟延时消息，到期先向支付宝二次确认再关单；每 30 秒的补偿任务扫描超过 40 分钟未关的订单兜底；三个触发源最终都汇聚到同一个状态机，靠条件更新保证恰好一次生效。
>
> 系统也有已知边界：数据库事务和消息发送之间存在毫秒级崩溃窗口，当前 MQ 只承担通知职责所以损失可容忍，根治方案是本地消息表，已列入演进计划。我的汇报完毕，请各位老师指正。

### 6.2 十分钟版（加讲部分，按时间取舍）

在五分钟版基础上插入两段：

**演进段**："项目的事件机制经历过三个阶段：最初用 Guava EventBus 做进程内事件总线，重启即丢；随后引入 RabbitMQ 获得持久化与重试；最终落地 RocketMQ，因为它的延时消息天然适配超时关单场景，重试与死信模型也更完整。每次迁移都由可靠性需求驱动，这是我从这个项目中学到的选型方法论。"

**测试段**："可靠性设计有端到端测试支撑：支付回调验签用自生成密钥对按生产同规则构造签名，走完整验签路径不绕过（`AlipayNotifyE2EIT`）；关单链路覆盖正常关单、重复关单防二次恢复、关单瞬间已支付的救援三个场景（`TimeoutCloseOrderE2EIT`）。"

### 6.3 预测追问 12 条（每条一句标准答，细节回读对应教材）

1. **"消息丢了怎么办？"** → 分发送时丢（S2，outbox 根治，未实现）与投递后丢（broker 持久化，消费失败重试 5 次进 DLQ 告警）；前提 P1-P3。【教材三 §5】
2. **"重复消费会不会重复扣库存？"** → 消费侧不承载库存扣减（恒空转）；真正扣库存走状态机条件更新。未来若下沉到消费侧，先落实 U-3。【教材三 §8-Q6、教材四】
3. **"高并发下怎么防超卖？"** → 三层（教材四 Q1）。
4. **"为什么不用分布式事务/Seata？"** → 成本与复杂度不匹配；本项目所有一致性用"条件更新裁判 + 幂等 + 对账兜底"实现最终一致，能逐场景论证方向安全。【教材四 §7.3】
5. **"Redis 挂了怎么办？"** → 消费幂等/库存闸门都依赖 Redis：下单扣减会失败拒绝（安全方向）；Job 锁拿不到则跳过本轮。都是 fail-safe 方向。【教材三 §9-D.12、教材四 §5 场景 6】
6. **"为什么用 RocketMQ 不用 RabbitMQ/Kafka？"** → 演进史 + 延时消息/重试/DLQ 语义匹配（§2.1 教材三 §7.4 口径；不编造换型动机）。
7. **"定时任务多实例会不会重复执行？"** → Redisson 锁 + 状态机幂等双保险（教材四 Q8）。
8. **"支付宝通知重复到达会怎样？"** → 验签 → canPay 守卫 → 条件更新影响行数 0 → 不发事件（TD-6）；四层幂等总表。【教材二】
9. **"扫码登录的安全性？"** → ticket 一次性 + 过期、JWT 无状态 + Redis 双凭证、绑定越权防护；附录 D 两项风险（未验签可伪造签发 token、二维码 30 天可重扫）已于 2026-10-19 实验确认，主动讲出 + 给修复方案。【教材一】
10. **"系统最大的不足是什么？"** → 主动说 S2 窗口 + 通知 best-effort + 无压测数据；每条都带升级路径。这是得分题，不是失分题。
11. **"如果流量涨 100 倍你先改哪里？"** → 先压测定位（诚实），预案方向：库存热点（Redis 闸门已就位）、DB 读写分离、MQ 扩容消费组——按教材七问式表达"收益/成本"。
12. **"这个项目你个人的贡献是什么？"** → 全部设计实现均为本人完成（毕设个人项目口径）；强调"每个设计决策都有源码和测试证据"，与实习经历区分。

## 8. 设计取舍：为什么升级顺序不能反

**U-1（兜底）→ U-2（根因）→ U-3（加固）→ U-4/U-5（运维）** 这个顺序的理由，本身就是一道面试题：

- 先做 U-2 outbox 而不做 U-1？outbox 只治"发出时丢"，消费端失败、进程宕机等其他缺口无人兜底——先兜底再治根因，每一步落地都能立刻降低总风险；
- U-5 自动化重放排在 U-3 之后？自动化重放依赖幂等键语义稳定（W3 窗口里重放会被误跳，教材三 §5.2），U-3 未落地时做自动化重放会放大事故；
- U-4 为什么最后？它是"资源效率"问题不是"正确性"问题，正确性闭环（U-1/U-2/U-3）完成前谈效率是本末倒置。

一句话：**升级路线的排序逻辑是"先让系统不丢事，再让系统不重复，最后让系统好运维"**——这句话可以直接放进答辩。
