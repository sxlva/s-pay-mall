## 一、对外 API 契约清单

### mall-api 体系（用户端 + 管理端）

完整 17+ 个端点见审计过程记录，以下是关键分类：

**用户端端点（`/mall-api/{version}/`）：**
- 认证：注册、登录、个人信息、微信绑定
- 商品：商品列表、分类列表
- 购物车：增删改查、清空
- 订单：创建、列表、继续支付、库存检查

**管理端端点（`/mall-api/{version}/admin/` 和 `/pay-api/{version}/admin/`）：**
- 两套并行的 admin 端点
- 用户/分类/商品/订单 CRUD + 统计数据

### 通用响应包装

`Response<T>`：`{code: String, info: String, data: T}` — 使用 `@Builder`，implements Serializable

## 五、后端 JSON 命名策略

| 层级 | @JsonProperty | JSON 输出 |

| `dto/` 包（Controller 实际返回） | **全部无** | **camelCase**（`orderId`, `price`, `payUrl`） |

## 六、前后端字段不一致清单

| 场景 | 后端 Java 字段 | JSON 实际输出 | 前端类型声明 | 前端实际读取 | 一致性 |
|---|---|---|---|---|---|
| 创建订单 orderId/orderNo | `OrderCreateRespDTO.orderId` | `"orderId"` | `OrderCreateResult.orderNo` | `CheckoutPage.vue` 写死 `''` | **不一致** — 硬编码空串 |
| 购物车价格 | `CartItemRespDTO.price` | `"price"` | `CartItem.productPrice` | `cartRepository.ts` 映射后读 `productPrice` | **运行时常一致**（映射层中转） |
| 订单列表 | `OrderListRespDTO.orderNo` | `"orderNo"` | `Order.orderNo` | `order.orderNo` | **一致** ✅ |
| 商品字段 | `ProductVO.categoryId` | `"category_id"` | `ProductVO.category_id` | `product.category_id` | **一致**（前端统一用下划线） |
| 库存检查 | `StockCheckRespDTO.success/message` | `"success"/"message"` | `StockCheckResult.success/message/stockStatus` | `stockResult.success/message` | **不一致** — 前端多余 `stockStatus` 字段，后端无对应 |

**需人工确认的疑似 bug**：`CheckoutPage.vue` 行 73-85 中 `initPayOrder({orderNo: '', …})` 和 `startPolling('', 180)` — 创建订单成功后后端返回的 `orderId` 未被提取传入支付轮询。

## 七、API 调用层次结构

```
src/api/          → 仅 admin.ts + order.ts（Axios 封装，覆盖管理端和订单 API）
src/repositories/ → 3 个 repository（cartRepository 用 bare fetch，其余用 Axios）
                     cartRepository: 补充 api/ 层未覆盖的购物车端点
                     orderRepository: 重复封装 + 补充（与 api/order.ts 重叠）
                     productRepository: 补充 api/ 层未覆盖的商品端点
src/services/     → 仅 adminUserService.ts（重复封装 admin.ts）
src/utils/        → axios.ts（2 个 Axios 实例，baseURL 均为 /mall-api/v1）
                     api.ts（通用 request 工具，未被 api/ 层使用）
src/hooks/        → 4 个 Hook，除 usePayment 新增 3 个辅助方法外，其余纯透传 store
```

## 八、模块依赖与打包分析

### 实际依赖方向（pom.xml 证实）

```
app → trigger → domain → types
              → api
              → infrastructure → domain
```

- `s-pay-mall-application` 模块**不存在**于磁盘上
- `OrderApplicationService` 位于 `trigger` 模块的 `cn.fcr.trigger.application` 包内
- P0-2 来源：b5ad008 commit 标记为"遗留项"——应用层暂放 trigger 模块，待建独立模块

### 循环依赖触发条件

当前**无循环依赖**。`OrderApplicationService` 的全部 import 来自 `cn.fcr.domain.*` + 同包 `OrderTransactionService`，无反向引用 trigger 层的 Controller/Listener/Converter/DTO。

若提取独立模块，需 `OrderApplicationService` + `OrderTransactionService` **一起移出**，否则产生 `trigger ↔ application` 循环。

### Fat JAR 丢失 trigger 代码可能性

- s-pay-mall-app 依赖 s-pay-mall-trigger 为 compile scope（默认）
- `spring-boot-maven-plugin` 缺少显式 `<executions>` 绑定，但 Spring Boot 2.7.x 会自动绑定 repackage
- 4 个子模块（trigger/domain/infrastructure/types）均配置了 `maven-archetype-plugin`，在 package 阶段执行 `create-from-project`，可能干扰正常打包
