# 系统升级点设计集（已设计、暂不实现）

> **文档定位**：本文件记录 s-pay-mall 在生产化演进方向上的升级点。每一项均已形成完整设计方案，但因毕业设计范围、部署规模（单实例演示）所限**暂不实现**。当答辩被追问"如果消息丢了怎么办 / 系统还有什么可以改进"时，可从本文档引用对应设计，说明演进路径。
>
> 已实现的可靠性现状：事务内状态推进 → 事务提交后发送 `order_paid` → 消费端 Redis SETNX 幂等（P0-4，E2E 锁定）→ RocketMQ 延时关单（延时等级 5 = 1 分钟）→ 消费失败重试（显式 `maxReconsumeTimes`）→ 死信队列（`%DLQ%` + consumerGroup）。

---

## U-1 对账补偿 Job（消息丢失的最后一道保险）

**解决什么问题**：MQ 可能"发出时就丢"——进程在事务提交后、消息发送前崩溃，`order_paid` 永远不会出现，重试和 DLQ 都救不回来。对账 Job 不依赖 MQ 可靠性，直接扫描数据库发现缺口。

**设计**：

- **支付补偿**：定时扫描 `pay_order = PAID` 但商城主单未推进、且超过 N 分钟的订单，直接调用 `paySuccess` 补偿。状态机已有保护（`orderStateMachineService.paySuccess` 重复推进仅 warn），补偿路径与 MQ 消费路径并发安全。
- **超时关单兜底**：扫描"超过超时时间仍待支付"的订单，调用 `handleTimeoutCloseOrder`。
- **N 的取值**：正常链路中延时关单 1 分钟内必有结果，故支付补偿 N 取 5~10 分钟（太小与正常 MQ 消费竞争，太大用户等待过久）；关单兜底扫 2 倍延时（约 2 分钟）仍未关闭的订单。
- **多实例防重**：Job 加 Redisson `tryLock`，抢不到锁直接跳过本轮（现有 `NoPayNotifyOrderJob` 为裸 `@Scheduled`，多实例下会重复执行，本项落地时一并修复）。
- **落点**：不新建组件，扩展现有 `NoPayNotifyOrderJob`，在其中增加两个检查分支。

**暂不实现的原因**：单实例演示环境 MQ 丢失概率极低，现有 NoPayNotifyOrderJob 已覆盖"回调丢失"场景；实现成本约 1~2 天，毕设性价比不足。

## U-2 发送端 Outbox（本地消息表，治"发出时丢"的根因）

**解决什么问题**："事务提交后发送"方案中，提交与发送之间仍有微小崩溃窗口。Outbox 把"发消息"变成和本地事务原子的一部分，从根因上消灭发送丢失。

**设计**：

- 支付回调事务内**同事务写入 outbox 表**：`id`、`biz_no`（业务单号，唯一索引）、`topic`、`payload`、`status`（待发送/已发送）、`retry_count`、`next_retry_time`。
- 独立 Job 扫描待发送记录，同步发送并检查 `SendResult`；成功改状态，失败累加次数、按退避更新 `next_retry_time`，超限告警。
- 已发送但状态未更新的记录会被重扫重发——**这是期望行为**：outbox 为至少一次投递，消费端幂等（见 U-3）保证重发无副作用。
- 成功记录不物理删除，仅标记状态，保留审计与排查能力。
- 表落 infrastructure 层，沿用 gateway 风格，application 层不直接拼 SQL。
- 备选方案为 RocketMQ 事务消息（需实现回查接口），对本项目规模而言 outbox 更易理解与排查，故不选。

**暂不实现的原因**：当前发送窗口已极小（事务同步回调内发送），U-1 对账 Job 可兜住残余概率；outbox 全链路（建表 + Job + 投递 + 告警）约 2~3 天，超出毕设范围。

## U-3 消费幂等升级：消费记录表替代 Redis 单键

**解决什么问题**：现状 `order_paid_notify:{orderNo}` 一个 Redis 键同时表示"处理中"和"已完成"，存在两个竞态：

1. 消费超时但业务已部分完成时，键仍在，MQ 重投被跳过 → 漏处理；
2. Redis 键设置与业务提交非原子，宕机中间态 → 可能重复执行。

库存 handler 的 `stock:event:{changeType}:{businessNo}` 存在同样问题。

**设计**：

- **推荐方案**：新增消费记录表，`(consumer_group, biz_no)` 唯一索引；插入记录与业务变更放在**同一个 DB 事务**中。宕机回滚时记录一并回滚，重投自然重新执行；提交成功则唯一索引天然拒绝重复。
- 备选方案：Redis 拆双状态——`PROCESSING` 短 TTL（略大于单次消费超时）、`DONE` 长 TTL；库存"检查 + 扣减"用 Lua 脚本保证原子。一致性弱于 DB 方案。
- **外部副作用（微信模板消息）无法进事务**，只能接受"至少一次"。两种取舍：重复发一条通知可接受（当前选择，JV-003 已记录为已知现象）；或加通知记录表去重（二期）。

**暂不实现的原因**：当前 Redis SETNX + 异常释放锁的方案已通过 P0-4 三场景 E2E（13/13），单机演示下竞态窗口极小；DB 方案涉及建表、事务改造与双 Handler 迁移，约 2~3 天。

## U-4 Listener 异常分类处理

**解决什么问题**：不可恢复错误（反序列化失败、订单不存在）重试 16 次毫无意义，白白占用重试资源、拉长告警时间。

**设计**：

- 可恢复异常（DB / Redis 抖动）继续抛出走重试；
- 不可恢复异常记录 error 日志后直接 ACK（不落失败记录表，避免"表没人看"的新问题；监控依赖日志告警）；
- 现状部分实践已符合：`paySuccess` 对"订单不存在"warn 后正常返回、超时关单对不存在订单直接忽略。本项将规则显式化并补充到开发规范。

**暂不实现的原因**：现状行为已接近目标，差异仅在"显式区分两类异常"的代码结构，毕设层面收益不明显。

---

## U-5 DLQ 监控告警与重放流程

**解决什么问题**：消息耗尽重试进入 `%DLQ%{consumerGroup}` 后，若无人处理则等于静默丢消息（对应技术债 P2-2）。

**设计**：

- 对 %DLQ% 主题配置告警：消息量 > 0 即报警，值班介入；
- 重放工具只投递给目标 consumer group，避免其他订阅方重复消费；重放前确认幂等键不会误判（24h TTL 已过期的需人工核实）；
- RocketMQ 控制台自带消息查询与重新发送，手工重放先以操作手册形式固化，自动化重放工具列为二期；
- 重放仍失败的转人工工单（order_paid 类消息人工核实后手动触发 paySuccess）。

**暂不实现的原因**：前三项（U-1~U-3）落地后进入 DLQ 的消息量趋近于零，告警与重放属于低频运维流程，毕设演示环境可用控制台手工操作替代。

---

## 演进顺序建议

U-1 对账 Job（含 NoPayNotifyOrderJob 分布式锁）→ U-2 outbox → U-3 消费记录表 → U-4 异常分类 → U-5 DLQ 告警与重放。

前一项落地会显著降低后一项的触发概率，整体呈"兜底 → 治根因 → 加固 → 运维"的递进结构。
