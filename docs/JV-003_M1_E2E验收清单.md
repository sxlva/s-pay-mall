## 〇、静态核实结论（验收前已确认，供对照）

**幂等证据链**（M1 正确性依赖于此）：

1. `OrderEntity.canPay()`（domain/mall/model/entity/OrderEntity.java:54）= `state == OrderState.INIT`——状态机守卫；
2. `OrderStateMachineServiceImpl.paySuccess()`（domain/mall/service/impl/OrderStateMachineServiceImpl.java:45-61）顺序：**先 `canPay()` 校验，通过才**更新 order_main、pay_order、`syncDBStockForPaySuccess()` 扣 MySQL 库存；
3. 因此 notify 同步处理完（state=PAID）后，`OrderPaidRocketListener` 再调 `paySuccess`：`canPay()`=false → **直接返回 false，不产生任何写操作和库存副作用**。监听器只保留微信通知职责；
4. 时序保障：`order_paid` 在事务方法 `changeOrderPaySuccessInTransaction` 返回（=事务提交）之后才发布（OrderApplicationService.java:250-259），监听器读到的一定是 PAID 后的数据；
5. 残留理论风险：`updateOrderStatusByOrderNo` 的 SQL 无 status 条件（OrderRepositoryImpl.java:139-145），并发极端场景（notify 与监听器同一毫秒）双写同值，幂等无业务损害，**可接受**。

## 〇-补、验收优先级（时间不够时的裁剪顺序）

- **P0-1 场景 1**：新订单正常支付回调 → `order_main=PAID` + `pay_order=已支付` + 库存 `S0−2`（三项缺一不可）

## 二、场景 1：新订单正常支付回调（验收矩阵第 1-7 行）

| # | 步骤 | 预期 | 检查方式 |
|---|------|------|---------|
| 1 | 用户 A 登录商城，加购 2 件商品 X，下单 | 返回 orderNo 和支付页 | 记录 orderNo；查 `product` 表商品 X 库存，记为 **S0** |
| 2 | 沙箱完成支付，等支付宝异步回调 | 回调返回 success | 日志出现 `pay_order 表状态已更新` 或 `【状态机】支付成功状态更新完成，orderNo=<orderNo>` |
| 3 | 查 order_main | `status = 'PAID'` | `SELECT order_no,status FROM order_main WHERE order_no='<orderNo>';` |
| 4 | 查 pay_order | `status = 'PAY_SUCCESS'`（或 PAID 码，以字典为准） | `SELECT order_id,status FROM pay_order WHERE order_id='<orderNo>';` |
| 5 | 查商品 X 库存 | 比 S0 **少 2**（Redis 预扣 + MySQL 同步扣减，数值一致） | `SELECT stock FROM product WHERE id=<商品X>;` 及 Redis `GET stock:<id>` |
| 6 | 查 order_paid 消息 | 已发布且被消费一次 | RocketMQ 控制台/日志：`OrderPaidRocketListener` 出现 `收到支付成功消息` + `订单状态更新成功` |
| 7 | 观察监听器行为 | 出现 `订单状态不允许支付...可能是重复回调`（warn）——**这正是幂等拦截的证明，不是错误** | 应用日志 |

场景 1 通过标准：**第 3、4、5 项全部符合，且库存只比 S0 少 2（一次）**。

## 三、场景 2：重复回调不重复扣库存（M1 **最核心**验收）

**制造重复回调的方法**（不用等支付宝自然重发）：用 Postman/Apifox **原样重放**场景 1 收到的支付宝回调报文（POST `/pay-api/v1/alipay/alipay_notify_url`，参数不变）。

**重放可行性已代码核实**：项目验签为纯参数 RSA 校验（`AlipayGatewayImpl.verifySignature` → `getSignCheckContentV1`，AlipayGatewayImpl.java:63-73），**无时间戳/nonce/通知ID防重**——原样重放必过验签。稳妥做法：先把第一次 notify 的完整参数保存下来再重放。

**硬验收标准（只看数据库终态，不看响应）**：

| # | 步骤 | 预期 |
|---|------|------|
| 1 | 第 1 次回调（场景 1） | `order_main=PAID` + `pay_order=已支付` + 库存 **S0−2** |
| 2 | 第 2 次重放同一回调 | 三表终态**不变**；库存**仍 S0−2**（日志出现状态机 `可能是重复回调` warn 是幂等拦截的证明，不是错误） |
| 3 | 第 3 次重放同一回调 | 同上 |
| 4 | 终态检查 | `order_main.status` 不变、`pay_order.status` 不变、库存全程只扣一次 |

> 注意：`update_time` 不作为判据（canPay 拦截后链路里是否有其他写操作以实测为准，只看 status 和库存）。

**已知现象（非缺陷，改动前即存在）**：每次重放都会再发一条 `order_paid`，监听器会**重复推送微信模板消息**（`sendPaymentNotification` 不在幂等保护内）。验收时若收到多条微信通知，属预期行为，记录在案即可，不在 M1 范围修复。
