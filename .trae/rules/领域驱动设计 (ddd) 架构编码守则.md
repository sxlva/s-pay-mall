## 1. 严格的分层架构依赖规范
- 依赖方向必须单向：用户接口层(Trigger) -> 应用层(Application) -> 领域层(Domain) <- 基础实施层(Infrastructure)。
- 严禁逆向依赖。

## 2. 核心层职责定位（绝对禁止跨界）
- **Trigger/User Interface 层**：仅负责接收请求、参数校验、DTO 与 Command/Query 的转换。**绝对禁止在此层编写任何业务逻辑或 Service 服务**。
- **Application 层**：负责编排领域服务和中转，不包含核心业务规则。
- **Domain 层**：核心业务逻辑的唯一所在地。所有的 Domain Service 必须且只能定义在这一层。
- **Infrastructure 层**：仅负责数据库、缓存、消息队列等技术实现（如 Repository 实现类）。**绝对禁止在此层越权编写核心业务逻辑**。

## 3. 稳健性与防崩盘修改规范
- **存量代码尊重原则**：在修改已有功能时，禁止重构或删除与当前需求无关的正常运行逻辑。
- **修改完备性**：所有修改必须完整，禁止生成“// 保持原样”等伪代码占位符。必须通盘修改所有受到影响的依赖类（如修改了 Service 接口，必须同步修改实现类）。
- **静态检查**：代码变更后，必须确保项目能够成功通过编译。
